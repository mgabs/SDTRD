# Specification: OpenSpec Addon

## Capability: `openspec-addon`

### 1. Functional Requirements

#### Schema
- **REQ-OSA-1 (Schema Bundle)**: The addon MUST ship a schema named `spec-rails` at `schemas/spec-rails/` (`schema.yaml` + `templates/`) that `openspec` resolves after being copied to `openspec/schemas/spec-rails/`.
- **REQ-OSA-2 (Research Artifact)**: The `spec-rails` schema MUST define a `research` artifact generating `research.md` with `requires: []`, and `proposal` MUST require `research`.
- **REQ-OSA-3 (Artifact DAG)**: The schema MUST define `research → proposal → specs → design → tasks`, matching `spec-driven` edges between `proposal`, `specs`, `design` and `tasks`.
- **REQ-OSA-4 (Gate Footers)**: Every artifact template MUST end with a `## Review Gate` section containing an unticked `- [ ]` approval checkbox naming its gate.
- **REQ-OSA-5 (Gate Instructions)**: Each artifact `instruction` MUST carry the Spec-Rails mandatory sections for its gate (Gate 0–4 per `WORKFLOW.md` §2), including Out-of-Scope (YAGNI) for proposals and Pure Core vs I/O Shell for designs.
- **REQ-OSA-6 (Slice Loop)**: `apply.instruction` MUST direct the agent through BDD scenarios → Gate 5.x approval → Red → Green → coverage → mutation per slice, and `apply.requires`/`tracks` MUST be `[tasks]` / `tasks.md`.

#### Spec Model
- **REQ-OSA-7 (Delta Specs)**: Feature specs MUST be OpenSpec delta specs under `openspec/changes/<id>-<slug>/specs/`; the full-copy rule is removed.
- **REQ-OSA-8 (Requirement Keys)**: Each delta requirement header MUST begin with its stable key: `### Requirement: REQ-<DOMAIN>-<N> <Name>` (and `NFR-` likewise); keys MUST NOT be reused.
- **REQ-OSA-9 (Archive)**: Gate 6 MUST use `openspec archive` for spec sync and archival; Spec-Rails MUST NOT copy into or move within any spec directory itself.
- **REQ-OSA-10 (Change Naming)**: Feature changes MUST be named `<id>-<slug>` with the roadmap ID lowercased (e.g. `w3.1-openspec-addon`).

#### Installer
- **REQ-OSA-11 (Prerequisite)**: The installer MUST fail with a non-zero exit and a message when the target has no `openspec/` directory, when `openspec` is not on `PATH`, or when its version is below the pinned minimum (`1.15.0`).
- **REQ-OSA-12 (Wiring)**: On a valid target the installer MUST: copy the schema to `openspec/schemas/spec-rails/`; set `schema: spec-rails` in `openspec/config.yaml`; install the pre-commit config, CI workflow, mutation templates, branch-protection hook, Spec-Rails agent rules; and ensure `.worktrees/` is in `.gitignore`.
- **REQ-OSA-13 (Idempotence)**: A second installer run MUST leave all files byte-identical and exit 0.
- **REQ-OSA-14 (Non-Destructive Config)**: The installer MUST preserve existing `openspec/config.yaml` keys other than `schema`, and MUST NOT overwrite an existing user `.pre-commit-config.yaml`.
- **REQ-OSA-15 (Update Survival)**: Spec-Rails skills and rules MUST NOT live in files regenerated by `openspec update`.

#### Enforcement
- **REQ-OSA-16 (Gate Check)**: A check runnable from pre-commit and CI MUST fail when, for any active change, an artifact exists whose preceding gate checkbox is unticked.
- **REQ-OSA-17 (Lane Check)**: The check MUST fail commits made directly on `main`/`master`.
- **REQ-OSA-18 (Status Source)**: The gate check MUST determine artifact presence via `openspec status --json`, not by re-implementing the artifact graph.

#### Parallel Streams
- **REQ-OSA-19 (Delta Rebase Discipline)**: `WORKFLOW.md` MUST require each stream to rebase onto the feature branch and pass `openspec validate <change>` before merge.

#### Migration
- **REQ-OSA-20 (Self-Migration)**: After W3.8, Spec-Rails's repo MUST contain no `specs/{features,living,archive}` directories; `WORKFLOW.md`, `README`, `rules/AGENTS.md`, `skills/spec-rails/SKILL.md` and docs MUST describe the `openspec/` layout.

### 2. Non-Functional Requirements & Budgets

- **NFR-OSA-1 (Dependencies)**: The installer and checks MUST be POSIX `sh`; no new runtime dependency beyond `openspec`, `git` and standard utilities (`jq` only if documented as required).
- **NFR-OSA-2 (Installer Latency)**: Install on a project with 0 changes MUST complete within 5 s excluding `openspec` startup.
- **NFR-OSA-3 (Gate Check Latency)**: The gate check MUST complete within 3 s on a project with 20 active changes, excluding `openspec status` calls.
- **NFR-OSA-4 (Portability)**: Scripts MUST run on macOS and Linux default shells.
- **NFR-OSA-5 (Rails)**: Installer and check scripts MUST have ≥ 95% line and branch coverage under the existing shell test suite and meet the mutation requirement where a mutation tool is available for the stack.

### 3. Assumptions & Edge Cases

- **ASM-OSA-1**: OpenSpec 1.x resolves schemas from `openspec/schemas/<name>/` and preserves unknown keys in `config.yaml`.
- **ASM-OSA-2**: Requirement headers containing a leading key are matched by OpenSpec as ordinary names for MODIFIED/REMOVED (to be verified at Gate 3).
- **Edge Case 1**: Target has `schema:` already set to another value → installer sets `spec-rails` and prints the previous value.
- **Edge Case 2**: `openspec/config.yaml` absent → installer creates it with only `schema: spec-rails`.
- **Edge Case 3**: Target is not a git repository → hooks are skipped with a warning; schema and config wiring still occur.
- **Edge Case 4**: No active changes → gate check exits 0.
- **Edge Case 5**: Malformed `openspec status --json` output → gate check exits non-zero with the parse error (no silent pass).

### 4. Behavioral Scenarios (Given / When / Then)

#### Scenario 4.1: Fresh install
- **Given** a repo initialized with `openspec init` and OpenSpec ≥ 1.15.0
- **When** the installer runs
- **Then** `openspec schemas` lists `spec-rails`, `config.yaml` has `schema: spec-rails`, and hooks, CI and rules are present (REQ-OSA-1, 11, 12)

#### Scenario 4.2: Idempotent re-run
- **Given** a completed install
- **When** the installer runs again
- **Then** no file changes and exit 0 (REQ-OSA-13)

#### Scenario 4.3: Missing prerequisite
- **Given** a directory without `openspec/`
- **When** the installer runs
- **Then** it exits non-zero with a message and writes nothing (REQ-OSA-11)

#### Scenario 4.4: Config preservation
- **Given** `config.yaml` with `context` and `rules`
- **When** the installer runs
- **Then** those keys are unchanged and `schema: spec-rails` is set (REQ-OSA-14)

#### Scenario 4.5: Research gates proposal
- **Given** a change using schema `spec-rails` with no `research.md`
- **When** `openspec status --change <c>` runs
- **Then** `proposal` is `blocked` on `research` (REQ-OSA-2, 3)

#### Scenario 4.6: Unticked gate blocks later artifacts
- **Given** a change whose `proposal.md` exists with an unticked Gate 1 box and a `specs/` artifact present
- **When** the gate check runs
- **Then** it exits non-zero naming the change and the unticked gate (REQ-OSA-16)

#### Scenario 4.7: Direct commit on main
- **Given** the current branch is `main`
- **When** the check/hook runs
- **Then** it exits non-zero (REQ-OSA-17)

#### Scenario 4.8: Malformed status output
- **Given** `openspec status --json` returns invalid JSON
- **When** the gate check runs
- **Then** it exits non-zero with the parse error (Edge Case 5)

#### Scenario 4.9: Archive uses OpenSpec
- **Given** a completed change on the feature branch
- **When** Gate 6 is executed
- **Then** specs are synced and archived by `openspec archive` with no Spec-Rails-owned copy or move step (REQ-OSA-9)
